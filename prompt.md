# MASTER PROJECT PROMPT: AI Persona-Based UX Testing Agent

## 1. Your Role

Act as a Senior AI Engineer, Python Backend Developer, Frontend Engineer, Browser Automation Engineer, and Solution Architect.

Your responsibility is to design and develop a complete, locally runnable **AI Persona-Based UX Testing Agent**.

Build this as a proper software engineering project with modular architecture, clean code, reusable components, error handling, documentation, and testing.

Do not create a basic chatbot or a simple browser automation script. We are building an AI agent that simulates different types of users interacting with web applications and identifies real usability and accessibility problems.

Work incrementally. First establish the project structure and foundation, then implement and test each module.

---

# 2. Project Vision

Traditional software testing primarily validates whether an application works functionally.

However, an application can be functionally correct and still provide a poor user experience.

Examples:

- A first-time user cannot find the registration button.
- An elderly user struggles to read small text.
- A low-vision user cannot distinguish buttons because of poor contrast.
- A non-native English speaker cannot understand technical terminology.
- An impatient user abandons a checkout process because it requires too many steps.
- A user submits a form but receives unclear error messages.
- A keyboard-only user cannot navigate important controls.

Our goal is to build an AI-powered testing platform that simulates these different users, navigates websites, detects UX friction, evaluates accessibility, and generates actionable reports.

### Main objective

Build an AI agent that can:

1. Understand a test objective.
2. Simulate a selected user persona.
3. Navigate a real web application using browser automation.
4. Decide what action to take based on the current page.
5. Identify usability problems, confusion, hesitation, and accessibility barriers.
6. Capture screenshots and execution evidence.
7. Generate prioritized UX findings with suggested fixes.
8. Allow a human reviewer to accept, reject, comment on, or resolve findings.

## AI / LLM

Use **Azure AI Foundry** as the LLM provider.

The model should support structured responses and, preferably, image/vision input.

Use the Azure AI Foundry model deployment configured through environment variables.

The LLM must be responsible for reasoning about the persona's next action.

Do not use a local LLM.

Do not hardcode model deployment names, endpoints, or API keys.

Create an abstraction layer so that the model provider can be changed later without rewriting the browser agent.

## Browser Automation

Use Python Playwright.

Important architectural decision:

The LLM must NOT generate arbitrary Playwright Python scripts and execute them dynamically.

Instead:

1. Playwright observes the current browser state.
2. The observation is sent to the Azure AI Foundry LLM.
3. The LLM returns a structured action.
4. Our Python Playwright controller validates the action.
5. The controller executes it.
6. Playwright captures the updated state.
7. The updated state is sent back to the LLM.
8. The cycle continues until the objective is completed or the agent stops.

Use a controlled action schema.

Supported initial actions:

- navigate
- click
- type
- fill
- scroll
- select
- press_key
- wait
- finish

Never execute arbitrary code generated by the LLM.

## Accessibility

Use axe-core for automated accessibility checks.

Because the primary browser automation framework is Python Playwright, implement axe-core integration in a compatible way, such as loading the axe-core JavaScript into the page and executing its accessibility scan.

Do not assume the Node.js `@axe-core/playwright` package can be imported directly into Python.

Evaluate:

- Color contrast
- Missing accessible names
- Missing form labels
- Missing image alt text
- Keyboard accessibility
- Heading structure
- Focus visibility
- Common WCAG violations

Automated accessibility testing does not replace manual accessibility testing. Clearly communicate this limitation in reports.

## Storage

Initially use the local filesystem for:

- Screenshots
- Browser execution history
- Accessibility results
- Findings
- Reports
- Execution metadata

Do not introduce PostgreSQL or Redis in the initial MVP unless genuinely required.

Design the storage layer so a database can be introduced later.

# 6. Core System Architecture

Build the following components.

## A. Test Orchestrator

File:

`backend/app/orchestrator/test_orchestrator.py`

Responsibilities:

- Receive test-run requests.

- Generate the final report.
- Update test-run status.

The orchestrator must coordinate components, not directly perform browser interactions.

## B. Persona Manager

File:

`backend/app/personas/persona_manager.py`

Manage predefined and customizable user personas.

Each persona must contain:

- Persona ID
- Name
- Description
- Experience level
- Technical familiarity
- Patience level
- Reading preference
- Navigation behaviour
- Accessibility requirements
- Viewport configuration
- Interaction preferences
- Task-completion expectations

Create at least five predefined personas.

### Persona 1: First-Time User

- No prior experience with the application.
- Explores the interface.
- Looks for obvious navigation options.
- May hesitate when instructions are unclear.
- Needs clear labels and feedback.

### Persona 2: Elderly User

- Prefers readable text.
- Requires clear buttons.
- Has lower tolerance for complicated navigation.
- Needs understandable instructions.
- May struggle with small interactive elements.

### Persona 3: Low-Vision User

- Requires readable visual content.
- Benefits from zoomed interfaces.
- Needs sufficient contrast.
- Relies on accessible names and keyboard navigation.
- May use accessibility-related browser settings.

### Persona 4: Non-Native English Speaker

- May struggle with technical language.
- Prefers simple and understandable instructions.
- May misunderstand ambiguous labels.
- Benefits from clear error messages.

### Persona 5: Impatient Power User

- Wants to complete tasks quickly.
- Prefers fewer steps.
- Avoids unnecessary instructions.
- Expects clear feedback.
- May abandon a slow or complicated process.

Important:

Personas must influence actual browser behaviour, not just change the LLM prompt.

Implement configurable behaviour such as:

- Navigation strategy
- Exploration behaviour
- Retry limits
- Reading/clarification preferences
- Viewport and zoom
- Tolerance for failed actions
- Decision-making preferences

Do not pretend simulated delays or LLM-generated emotions are genuine human measurements. Distinguish simulated behaviour from objectively measured browser events.

## C. AI Browser Agent

File:

`backend/app/agents/browser_agent.py`

This is the primary AI agent.

Responsibilities:

1. Receive the task objective.
2. Receive persona information.
3. Obtain the current browser observation.
4. Send relevant context to Azure AI Foundry.
5. Ask the LLM to determine the next action.
6. Parse its structured response.
7. Validate the response.
8. Ask the Playwright controller to execute the action.
9. Observe the resulting page.
10. Record evidence and continue.

The agent must maintain context across multiple browser steps.

Use a structured Pydantic action model.

Example response:

```json
{
  "action": "click",
  "target": "Create an account",
  "reason": "The user needs to find the registration page.",
  "expected_result": "Registration form should appear",
  "confidence": 0.92
}
```

Also support:

- Successful completion
- Failed action
- Unclear page state
- Retry
- Abandonment
- Maximum-step termination

Do not allow an infinite action loop.

Use a configurable step limit.

## D. Playwright Controller

File:

`backend/app/browser/playwright_controller.py`

Responsibilities:

- Launch Chromium.
- Open the target URL.
- Manage browser contexts.
- Capture page information.
- Execute supported browser actions.
- Capture screenshots.
- Collect page URL and title.
- Handle timeouts and browser errors.
- Close browser sessions safely.

Implement robust locator strategies.

Prefer:

1. Accessible roles and names.
2. Labels.
3. Placeholder text.
4. Visible text.
5. CSS selectors when necessary.

Do not depend exclusively on fragile CSS selectors.

Do not allow the LLM to execute arbitrary browser JavaScript.

## E. Page Observer

`backend/app/browser/page_observer.py`

Collect:

- Current URL
- Page title
- Visible text
- Accessibility snapshot or equivalent structured DOM information
- Available interactive elements
- Form fields
- Buttons and links
- Relevant page metadata
- Screenshot

Keep observations concise enough for the LLM context window.

Support screenshot-based analysis when the selected model supports vision.

## F. Evidence Collector

`backend/app/evidence/evidence_collector.py`

Save:

- Action history

- Action attempted

- LLM decision

- Final outcome

## G. UX Analyzer

Identify:
